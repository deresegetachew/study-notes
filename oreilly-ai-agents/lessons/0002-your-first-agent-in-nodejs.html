Your First Agent in Node.js

Implement the agent loop from scratch — no framework, just the raw loop — so you know exactly what every framework does under the hood.

What you'll build

A command-line agent that can answer questions requiring tool use. You give it a task like "What files are in my current directory and how many are there?" — and it will call a real tool (a shell command runner), observe the result, and return an answer.

No LangChain, no Vercel AI SDK. Just the Anthropic SDK and the loop you learned in Lesson 1.

Step 1 — Project setup

1

Create a new project and install the Anthropic SDK:

mkdir my-first-agent && cd my-first-agent
npm init -y
npm install @anthropic-ai/sdk
touch agent.mjs

We use .mjs for top-level await without extra config.

2

Add your API key. Create a .env file (and add it to .gitignore):

echo "ANTHROPIC_API_KEY=sk-ant-..." > .env
echo ".env" >> .gitignore
Don't have a key? Get one at console.anthropic.com. The free tier is enough for this lesson. Haiku is cheapest — we'll use it here.

Step 2 — The agent loop

Before you write code, re-read the loop from Lesson 1. Every line you write maps to one of these steps:

Course reference: Level 2, §2.5 — "Create an Agent Class from Scratch". The Python version of this same loop is on slide 26 onwards.
  1. Send goal + context + available tools → LLM
  2. LLM returns: text response or a tool call
  3. If tool call: execute it, append result to messages
  4. Repeat from 1 until LLM returns plain text

Here is the full agent in one file. Read through it once — annotations explain each part:

// agent.mjs
import Anthropic from '@anthropic-ai/sdk';
import { execSync } from 'child_process';

const client = new Anthropic({
  apiKey: process.env.ANTHROPIC_API_KEY,
});

// ── 1. DEFINE TOOLS ──────────────────────────────────────────────────────────
// A tool is just a JSON schema + a handler function.
// The LLM reads the schema to decide when and how to call the tool.
// Your code runs the handler and returns the result.

const tools = [
  {
    name: 'run_shell',
    description: 'Run a safe, read-only shell command and return its output. Use for listing files, checking environment, reading file contents.',
    input_schema: {
      type: 'object',
      properties: {
        command: {
          type: 'string',
          description: 'The shell command to run (read-only operations only)',
        },
      },
      required: ['command'],
    },
  },
];

// ── 2. DEFINE TOOL HANDLERS ───────────────────────────────────────────────────
// This is the code that actually executes when the LLM calls a tool.
// Think of this as a NestJS service method the LLM is allowed to invoke.

function executeTool(name, input) {
  if (name === 'run_shell') {
    try {
      return execSync(input.command, { encoding: 'utf8', timeout: 5000 });
    } catch (err) {
      return `Error: ${err.message}`;
    }
  }
  return 'Unknown tool';
}

// ── 3. THE AGENT LOOP ─────────────────────────────────────────────────────────
// This is the core. It is exactly the 4-step loop from Lesson 1.

async function runAgent(userMessage) {
  console.log(`\n🤖 Task: ${userMessage}\n`);

  // The messages array IS the agent's memory.
  // Every turn — user message, assistant response, tool result — appends here.
  const messages = [
    { role: 'user', content: userMessage }
  ];

  while (true) {
    // STEP 1: Send current state to the LLM
    const response = await client.messages.create({
      model: 'claude-haiku-4-5-20251001',
      max_tokens: 1024,
      tools,
      messages,
    });

    // STEP 2: Check what the LLM returned
    const stopReason = response.stop_reason;

    if (stopReason === 'end_turn') {
      // LLM returned a plain text answer — we're done
      const text = response.content
        .filter(b => b.type === 'text')
        .map(b => b.text)
        .join('');

      console.log(`\n✅ Answer:\n${text}\n`);
      return text;
    }

    if (stopReason === 'tool_use') {
      // LLM wants to call a tool — append its response to messages first
      messages.push({ role: 'assistant', content: response.content });

      // STEP 3: Find tool calls, execute each, collect results
      const toolResults = response.content
        .filter(b => b.type === 'tool_use')
        .map(toolCall => {
          console.log(`  🔧 Tool: ${toolCall.name} → ${JSON.stringify(toolCall.input)}`);
          const result = executeTool(toolCall.name, toolCall.input);
          console.log(`  📋 Result: ${result.slice(0, 120)}...`);
          return {
            type: 'tool_result',
            tool_use_id: toolCall.id,
            content: result,
          };
        });

      // Append tool results — the LLM will read these on the next iteration
      messages.push({ role: 'user', content: toolResults });

      // STEP 4: Loop — go back to top and call the LLM again
    }
  }
}

// ── 4. RUN IT ─────────────────────────────────────────────────────────────────

await runAgent(
  'List the files in the current directory and tell me how many there are.'
);

Step 3 — Run it

node --env-file=.env agent.mjs

You should see output like this:

Terminal output
🤖 Task: List the files in the current directory and tell me how many there are. 🔧 Tool: run_shell → {"command":"ls -la"} 📋 Result: total 32 drwxr-xr-x 4 user staff 128 Jun 14 ... ✅ Answer: The current directory contains 4 items: - agent.mjs - node_modules/ - package.json - package-lock.json

What just happened: the LLM decided to call run_shell, your code executed it, the result was fed back in, and then the LLM synthesised a human-readable answer. That is the full agent loop — you built it from scratch.

What frameworks actually do

Now you know the loop. Every framework — LangChain, Vercel AI SDK, LangGraph — wraps this exact same pattern. They add:

  • Convenience for defining and registering tools
  • Built-in error handling and retries
  • Streaming support
  • Graph-based control flow (for multi-agent setups)
  • Observability hooks

None of them change the core loop. When something breaks in a framework, you now know where to look.

Stretch: try a second task

Change the last line to a task that requires multiple tool calls to answer. For example:

await runAgent(
  'Read the contents of package.json and tell me what version of Node this project expects.'
);

Watch the loop iterate more than once. The LLM will call ls, then cat package.json, then synthesise an answer from both results.

⚡ Engineering tensions
Custom ReAct vs. framework—Building ReAct from scratch gives total control and transparency. Using a framework is faster but hides loop mechanics. The right choice depends on whether you need to modify the loop logic or just need a working agent quickly.
System prompt verbosity vs. LLM comprehension—A longer, more explicit system prompt (with examples, edge cases, tool usage rules) produces more reliable behavior but consumes tokens on every call. Find the minimum prompt that produces reliable behavior for your specific task.
Tight loop control vs. agent flexibility—A hand-rolled loop with explicit regex parsing for Action lines gives total control but breaks if the LLM changes output format. Framework-based loops handle variation but are harder to customize for non-standard behavior.
Max turns as safety vs. performance ceiling—Low max_turns is safe but limits complex tasks. High max_turns enables complex tasks but risks runaway loops. Set at ~2× your P95 turn count to catch outliers without strangling normal operation.
💬 Staff-level questions
Q1
Your custom ReAct agent enters a loop where it repeatedly calls the same tool with slightly different arguments without making progress. How do you detect and break this?
Steer: Detect repetition, not just max_turns. Same tool + similar arguments is a stuck signal.
Detection: maintain a tool_call_history in state: Annotated[list, add]. After each tool call, append (tool_name, hash_of_args). Before the next tool call, check: if the last 2 entries have the same tool_name and similar args hash (fuzzy match), the agent is stuck. Breaking the loop: inject a system message into the conversation: 'You have called [tool_name] multiple times with similar arguments without new information. Please either try a different approach, use a different tool, or provide a best-effort answer based on available information.' This redirects without hard-stopping. If still stuck after 2 more turns: force termination and return a partial result with explanation. Track 'stuck detected' as a metric — high rate indicates the tools or prompt need redesign for the stuck query pattern.
Q2
The LLM stops generating 'PAUSE' tokens and includes the action result inline. What has changed and how do you fix it?
Steer: The LLM's output format drifted. This happens because the format instruction wasn't strong enough or the model changed.
Root causes: (1) Model version updated and the new version follows PAUSE instructions less reliably. (2) System prompt was changed and the PAUSE instruction got deprioritized or buried. (3) Conversation history grew long enough that the PAUSE instruction got pushed out of the attention window. Fix: (1) Add PAUSE instruction at the end of the system prompt (better attention to end positions). (2) Add it again as a reminder in the user message template: 'Remember: output PAUSE after each Action and wait for the Observation.' (3) If model version changed: test whether the new version follows PAUSE consistently. Some newer models prefer a different format (e.g., tool_call objects rather than text-based PAUSE). Switch to the framework's built-in tool calling mechanism rather than text-based PAUSE — it's more reliable across model versions. (4) Reduce message history length — if PAUSE compliance drops after 8 turns, implement history pruning to keep the system prompt instructions visible.
Q3
Why does the message history need to be passed to every LLM call, and what breaks if you only pass the latest message?
Steer: LLMs are stateless. The history IS the state.
LLMs are completely stateless between API calls — they have no memory of previous calls. Passing only the latest message: the LLM sees 'Action: search for X' as its entire context. It has no idea: (1) What the original task was (system prompt is gone if you don't include it), (2) What previous searches returned (Observations are gone), (3) What the user originally asked (their message is gone), (4) What tools are available (forgotten without system prompt). The result: the LLM either hallucinates context or gives a nonsensical response. Every call must include the full history: [system_message, user_message, assistant_turn_1_thought, tool_result_1, assistant_turn_2_thought, ...]. This is expensive (every call pays for the full history in tokens) but necessary. Optimization: compress old turns into summaries, not eliminate them.
Q4
What are the 4 essential elements of an effective ReAct system prompt, and what goes wrong if each is missing?
Steer: Each element serves a specific purpose. What does the LLM do without it?
(1) Loop format instructions ('You run in a loop: Thought → Action → PAUSE → Observation'): Without this, the LLM doesn't know to alternate thinking and acting. It might do all thinking first, or skip thinking entirely. (2) Available tools list with examples ('Available tools: search_inventory(product_id) → returns stock info'): Without this, the LLM doesn't know what tools exist and may hallucinate tool calls or call non-existent tools. (3) PAUSE instruction ('After each Action, output PAUSE and wait for the Observation'): Without this, the LLM generates both the Action and a hallucinated Observation without waiting for the real tool result. This is the most critical instruction to get right. (4) Example session (shows a complete Thought/Action/PAUSE/Observation/Answer exchange): Without this, the LLM understands the instruction abstractly but may not format the output correctly. The example is the template the LLM replicates.
Q5
How do you handle the case where a tool call returns a response too long to include fully in the context?
Steer: Tool results can be large (e.g., a full document, search results with 100 items). Including them fully fills the context window.
Three strategies: (1) Summarize at the tool level: the tool itself truncates or summarizes its output. search_results returns top 5 results, not 100. The truncation logic is in the tool, not the agent. (2) Summarize in the Observation: after receiving the tool result, run a cheap LLM call to compress it: 'Summarize these search results in 100 words.' Pass the summary as the Observation, not the full result. Store the full result externally (file system, database) with an ID in state. (3) Extract and structure: parse the large response and extract only the fields the agent needs. If the tool returns a full JSON document, extract the 3 fields the agent cares about and discard the rest. Track context window utilization — if tool results are regularly consuming >30% of the context, implement one of these patterns proactively.
Q6
Design a monitoring dashboard for a production ReAct loop. What 5 metrics would you display?
Steer: Metrics should answer: is it working? Is it efficient? Is anything wrong?
(1) Max_turns hit rate (target: <1%) — the most critical signal. Any spike means agents are getting stuck. Alert at 2%. (2) Average turns per successful run (P50/P95) — track over time. Increasing P95 means tasks are getting harder or the agent is getting less efficient. (3) Tool call error rate by tool name — identifies which specific tools are failing. (4) Cost per successful run (tokens × price) — tracks efficiency over time and catches runaway loops early. (5) Task completion rate (completed / started) — how many agent runs produce a final answer vs. timing out or erroring. Each metric at P50/P95/P99 over a 24h rolling window. Drill-down: clicking any metric should show the runs that contributed to anomalies.
Q7
The loop hits max_turns on every complex query. What changes do you make — to the system prompt, tools, or max_turns?
Steer: Diagnose first: are the queries genuinely complex, or is the agent inefficiently approaching them?
Diagnose: log the full turn sequence for 10 failing runs. Common patterns: (1) Agent keeps searching for specific information the tools cannot provide → fix the system prompt: 'If you cannot find X after 2 searches, provide a best-effort answer stating the limitation.' (2) Agent verifies every piece of information multiple times → add to system prompt: 'Trust your tool results. Do not re-verify information you've already retrieved.' (3) Queries are genuinely complex requiring many steps → raise max_turns for this query type only. Add a query complexity classifier; set max_turns=20 for complex queries, max_turns=5 for simple ones. (4) Tools return incomplete results requiring many follow-up calls → redesign the tools to return richer, more complete data in a single call. Fix the root cause, not just the symptom.

🔴 Production pitfalls
Message history growing without boundsEvery turn appends to the message list. After 15 cycles, you may have 45+ messages consuming most of the context window. Implement history trimming or summarization for multi-turn agents.
No distinction between recoverable and terminal failuresA tool returns 'API key invalid' — that's terminal, retrying won't help. A tool returns '429 rate limited' — that's recoverable. The agent should handle these differently: terminal errors escalate immediately, recoverable errors retry. Without this distinction, the agent wastes turns retrying terminal errors.
Silent max_turns failuresThe loop hits max_turns and returns empty or None with no explanation. Always return the best available partial result plus an explicit explanation when terminating on max_turns. Log a WARNING.
Regex brittle to LLM output variationModel updates change output formatting. A regex that worked on gpt-4o-2024-05-13 breaks on gpt-4o-2024-08-06. Add fallback parsing strategies and monitor fallback fire rates.
