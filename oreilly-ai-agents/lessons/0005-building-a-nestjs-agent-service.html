Building a NestJS Agent Service

Everything from lessons 1–4 assembled into a real API. Agent loop, tool use, thread persistence — all wired through NestJS dependency injection with an HTTP endpoint you can call from any client.

Why expose an agent as an HTTP service

Course ref: Level 3, §3.12 — Deploying Agents with FastAPI. NestJS plays the same role as FastAPI here — it is just the HTTP layer. The agent logic underneath is identical.

The scripts you built in lessons 2–4 run on your machine, called from your terminal. An HTTP service means:

  • Any client — web app, mobile, Slack bot, another service — can talk to your agent
  • Multiple users concurrently, each with their own thread
  • NestJS handles request parsing, validation, error serialisation, and DI for free

1 — The DTO

This is the NestJS equivalent of a Pydantic model. It validates the request body before it ever reaches your service — bad input gets rejected at the boundary with a clear error.

src/agent/chat.dto.ts
import { IsString, IsNotEmpty, IsOptional, MaxLength } from 'class-validator';

export class ChatRequestDto {
  @IsString()
  @IsNotEmpty()
  @MaxLength(4000)
  message: string;

  @IsString()
  @IsOptional()
  threadId?: string;  // omit to start a new thread
}

export class ChatResponseDto {
  reply: string;
  threadId: string;
}

2 — The thread repository

In-memory for now. To swap to Postgres, replace the Map with a TypeORM or Prisma repository — the service code does not change.

src/agent/thread.repository.ts
import { Injectable } from '@nestjs/common';

export type Message = { role: 'user' | 'assistant'; content: string };

@Injectable()
export class ThreadRepository {
  private readonly store = new Map<string, Message[]>();

  load(threadId: string): Message[] {
    return this.store.get(threadId) ?? [];
  }

  save(threadId: string, messages: Message[]): void {
    this.store.set(threadId, messages);
  }
}

3 — The agent service

This is the core. It contains the agent loop from lesson 2, the tool execution from lesson 3, and the thread persistence from lesson 4 — assembled into one injectable service.

src/agent/agent.service.ts
import { Injectable } from '@nestjs/common';
import Anthropic from '@anthropic-ai/sdk';
import { randomUUID } from 'crypto';
import { ThreadRepository, Message } from './thread.repository';
import { ChatResponseDto } from './chat.dto';

@Injectable()
export class AgentService {
  private readonly client: Anthropic;

  // ── TOOL DEFINITIONS ──────────────────────────────────────────────────────
  private readonly tools: Anthropic.Tool[] = [
    {
      name: 'get_current_time',
      description: 'Returns the current UTC date and time as an ISO 8601 string. Use when the user asks about the current time or date.',
      input_schema: { type: 'object', properties: {}, required: [] },
    },
    {
      name: 'calculate',
      description: 'Evaluate a simple mathematical expression and return the numeric result. Use for arithmetic. Do NOT use for anything non-numeric.',
      input_schema: {
        type: 'object',
        properties: {
          expression: {
            type: 'string',
            description: 'A safe mathematical expression, e.g. "12 * 4 + 7"',
          },
        },
        required: ['expression'],
      },
    },
  ];

  constructor(private readonly threads: ThreadRepository) {
    this.client = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY });
  }

  // ── TOOL EXECUTION ────────────────────────────────────────────────────────
  private executeTool(name: string, input: Record<string, unknown>): string {
    switch (name) {
      case 'get_current_time':
        return new Date().toISOString();
      case 'calculate': {
        try {
          // Safe eval: only allow digits and math operators
          const expr = (string)(input.expression).replace(/[^0-9+\-*/.() ]/g, '');
          return String(Function('"use strict"; return (' + expr + ')')());
        } catch {
          return 'Error: invalid expression';
        }
      }
      default:
        return 'Unknown tool';
    }
  }

  // ── AGENT LOOP ────────────────────────────────────────────────────────────
  async chat(userMessage: string, threadId?: string): Promise<ChatResponseDto> {
    const tid = threadId ?? randomUUID();
    const history = this.threads.load(tid);

    const messages: Anthropic.MessageParam[] = [
      ...history,
      { role: 'user', content: userMessage },
    ];

    let reply = '';

    while (true) {
      const response = await this.client.messages.create({
        model: 'claude-haiku-4-5-20251001',
        max_tokens: 1024,
        system: 'You are a helpful assistant. You have access to tools for time and arithmetic.',
        tools: this.tools,
        messages,
      });

      if (response.stop_reason === 'end_turn') {
        reply = response.content
          .filter(b => b.type === 'text')
          .map(b => b.text)
          .join('');
        break;
      }

      if (response.stop_reason === 'tool_use') {
        messages.push({ role: 'assistant', content: response.content });

        const results = response.content
          .filter(b => b.type === 'tool_use')
          .map(t => ({
            type: 'tool_result' as const,
            tool_use_id: t.id,
            content: this.executeTool(t.name, t.input as Record<string, unknown>),
          }));

        messages.push({ role: 'user', content: results });
      }
    }

    // Persist the updated thread
    this.threads.save(tid, [
      ...history,
      { role: 'user', content: userMessage },
      { role: 'assistant', content: reply },
    ]);

    return { reply, threadId: tid };
  }
}

4 — The controller

Thin by design. It validates input (via the DTO + ValidationPipe), calls the service, and returns the response. No agent logic lives here.

src/agent/agent.controller.ts
import { Body, Controller, Post } from '@nestjs/common';
import { AgentService } from './agent.service';
import { ChatRequestDto, ChatResponseDto } from './chat.dto';

@Controller('agent')
export class AgentController {
  constructor(private readonly agent: AgentService) {}

  @Post('chat')
  chat(@Body() dto: ChatRequestDto): Promise<ChatResponseDto> {
    return this.agent.chat(dto.message, dto.threadId);
  }
}

5 — Wire it in the module

src/agent/agent.module.ts
import { Module } from '@nestjs/common';
import { AgentController } from './agent.controller';
import { AgentService } from './agent.service';
import { ThreadRepository } from './thread.repository';

@Module({
  controllers: [AgentController],
  providers: [AgentService, ThreadRepository],
})
export class AgentModule {}

Swapping the thread store for Postgres

When you are ready for persistence across server restarts, replace ThreadRepository internals only. The service and controller do not change at all: 

// thread.repository.ts — Postgres version (TypeORM sketch)
@Injectable()
export class ThreadRepository {
  constructor(@InjectRepository(ThreadEntity) private repo: Repository<ThreadEntity>) {}

  async load(threadId: string): Promise<Message[]> {
    const thread = await this.repo.findOne({ where: { id: threadId } });
    return thread?.messages ?? [];
  }

  async save(threadId: string, messages: Message[]): Promise<void> {
    await this.repo.upsert({ id: threadId, messages }, ['id']);
  }
}

▲ Senior & Staff Deep Dive Engineering tensions • staff-level questions with answers • production pitfalls
▶
⚡ Engineering tensions
Speed to prototype vs. production readiness—create_agent() gives you a working agent in minutes with zero infrastructure. But you're building on abstractions you don't control. When something goes wrong in production, that magic becomes a debugging obstacle.
Model selection vs. cost—gpt-4o produces better routing decisions than gpt-4o-mini but costs 10–20× more per token. For agents calling the LLM at every step, model choice is your largest cost lever. Most production systems use cheaper models for simple routing and more capable models for complex reasoning.
Log verbosity vs. cost—Full trace logging (every prompt, every response) can produce 100× more data than the agent's actual output. Log structure, not content: tool name + type + latency + result status, not the full prompt text.
LangSmith convenience vs. data privacy—LangSmith makes debugging beautiful but sends full prompts and responses to LangChain's servers. For enterprise customers with data residency requirements, this may be unacceptable.
💬 Staff-level questions
Q1
You prototyped with create_agent() and it works. How do you decide whether to ship the prototype or rebuild before production?
Steer: The question is: what does production require that the prototype doesn't have?
Evaluate against the production checklist: (1) Does create_agent() give you the observability you need? Can you log every tool call with input/output/latency? If not, rebuild with a custom loop that adds logging. (2) Can you add guardrails and input validation in front of create_agent()? Usually yes — wrap it. (3) Is the error handling sufficient? create_agent() will propagate exceptions; you need to catch them and return clean responses. Wrap the invocation in try/except. (4) Is the state management sufficient for your use case? If you need cross-session persistence, create_agent() needs a checkpointer — add one. Decision: ship if you can add the missing production components as wrappers without touching the core. Rebuild if the fundamental loop logic needs modification.
Q2
Your pre-built agent starts hallucinating tool call arguments for a specific query pattern. Walk through the debugging process.
Steer: The tool call arguments come from the LLM's output. The LLM generates what it was instructed to generate.
Step 1: Log the exact prompt and response at the point of hallucination. What did the LLM receive? Step 2: Check the tool schema — is the parameter type or name ambiguous? A parameter called 'id' could be a product ID, order ID, or user ID. Make it specific. Step 3: Check if the query pattern contains words that could confuse the argument generation — 'search for order 1234' might generate order_id='order 1234' (including the word 'order'). Add examples to the docstring: 'order_id: the numeric ID only, e.g., 1234 not order-1234.' Step 4: Check if similar tool calls work correctly. If the same tool works for other queries, the issue is the specific query pattern interacting with the parameter generation. Add a few-shot example for this query pattern in the system prompt. Step 5: Add output validation — before executing the tool, validate that the arguments match expected types and formats.
Q3
Design a cost optimization strategy for an agent handling both simple and complex queries.
Steer: Not all queries need the same model. Route to the cheapest model that can handle the task correctly.
Two-tier routing: classify query complexity first (cheap, fast operation). Simple queries (single-fact lookup, standard templates) → route to gpt-4o-mini or equivalent. Complex queries (multi-step reasoning, ambiguous intent, synthesis) → route to gpt-4o. Complexity classifier: a fast, cheap LLM call or a heuristic (query length, presence of conjunctions, number of entities). Track quality by tier: measure output quality for both tiers to verify the cheap model handles simple queries adequately. Additional optimizations: (1) Cache responses for repeated identical queries. (2) Reduce context for simple queries — don't send full conversation history if the query is clearly self-contained. (3) Set max_tokens per query complexity tier — simple queries rarely need 1000 token responses.
Q4
What temperature should you set for each component of your agent, and why do different components need different temperatures?
Steer: Temperature controls randomness. Different components need different levels of randomness.
Temperature 0: routing decisions, tool selection, structured output generation, classification. These need deterministic, reproducible behavior. The same input must produce the same routing decision. Temperature 0.1–0.3: factual question answering, code generation, data extraction. Slight randomness allows finding slightly different phrasings, but answers should remain stable. Temperature 0.7–1.0: creative tasks, writing assistance, brainstorming. High variance is desired here. In practice: most agent components (routing, tool calling, structured extraction) run at temperature 0. Only the final response generation step, if it involves natural language synthesis, might benefit from temperature 0.2–0.5. Never use the default temperature (often 0.7–1.0) for agent decision-making — it makes behavior non-reproducible and hard to test.
Q5
How do you pin a model version in production, and what is your upgrade process when a new model version is released?
Steer: Model upgrades can silently change agent behavior. You need a deliberate upgrade process.
Pinning: always specify the exact model version string in code or config: 'gpt-4o-2024-05-13' not 'gpt-4o'. Store the model version in config, not hardcoded — makes it configurable per environment. Upgrade process: (1) New version announced — run your full test suite against the new version in a dev environment. (2) Run behavior comparison: for 100 production queries, compare outputs between old and new version using LLM-as-judge. Flag any responses where quality degrades or behavior changes. (3) If tests pass: deploy to 5% of traffic (canary). Monitor error rates, quality scores, and latency. (4) If canary passes for 48 hours: full rollout. (5) Keep old version pinned as rollback target for 2 weeks post-upgrade. Maintain a model version changelog: when did you upgrade, what changed, what tests were run.
Q6
Design a logging schema that lets you replay any production run and compute cost per successful run without logging PII.
Steer: You need enough to reconstruct the run without capturing sensitive content.
Schema: {run_id, timestamp, level, node_name, tool_name, tool_input_schema (not values), tool_output_status, input_tokens, output_tokens, latency_ms, customer_id_hash (hashed, not raw)}. For replay: log every state field that the agent writes, but mask any field tagged as PII (user_name → '[REDACTED]', email → '[REDACTED]'). For cost: input_tokens × input_price + output_tokens × output_price per event, summed by run_id. For replay: log state snapshots at each node transition — the sequence of {node, state_snapshot} is sufficient to reconstruct the run's logic path. Test: run 10 production cases, delete the agent, attempt replay from logs. If replay succeeds for all 10, your logging is sufficient.
Q7
Your observability shows P95 latency spiked 3× for 20 minutes. Walk through the debugging process using only logs.
Steer: The 20-minute window is the diagnostic frame. What changed in that window?
Step 1: Filter logs to the 20-minute window. Step 2: Check error rates — did errors spike alongside latency? If yes, failing retries are adding latency. If no, the work is taking longer (not failing more). Step 3: Check tool latency in that window — sort by tool latency P95. Did any specific tool's latency spike? External dependency issue. Step 4: Check turn count distribution — did the average turns per run increase? Model behavior change or new query types arriving. Step 5: Check which new deployments happened before the spike (correlation, not causation). Step 6: Check LLM API status page for that time window — provider incidents cause exactly this pattern. Step 7: Sample 5 slow runs from the spike window. Trace their tool call sequences. What were they doing? This usually identifies the root cause within 15 minutes.
Q8
How do you build a logging system that captures enough for debugging but stays within budget on log storage costs?
Steer: Different events need different retention periods and verbosity levels.
Tiered logging: (1) Always log (90-day retention): run_id, customer_id_hash, status, total_latency_ms, total_cost, node_sequence. Minimal footprint, enables all aggregate metrics. (2) On error or anomaly (30-day retention): full node sequence with state snapshots (PII-masked), all tool calls with input schemas and output statuses, error details. Only stored for ~5% of runs that have issues. (3) Debug mode (7-day retention, sampling): full verbose logs for 1% of traffic — enables sampling-based analysis. (4) Never log: raw user messages (PII risk), full tool outputs (volume), full LLM prompts (volume). Estimate: tier 1 at 500 bytes/run × 1M runs/day × 90 days = 45GB. Tier 2 at 50KB/error × 50K errors/day × 30 days = 75GB. Total: ~120GB — manageable at any cloud logging price.
🔴 Production pitfalls
Temperature 1.0 on agentsDefault temperature on most SDKs is 0.7–1.0. An agent with high temperature makes different routing decisions for identical inputs, making behavior non-deterministic. Always set temperature=0 for agent decision-making.
No observability wrapper around create_agent()create_agent() is a black box. Before shipping, wrap every invocation in a logging decorator that records: input message, output message, all tool calls made, total latency, total tokens. Without this you're flying blind in production.
PII in logsAn agent that processes customer data will have PII in its state, prompts, and tool results. Implement log sanitization at the source — mask PII fields before writing to logs.
Logging full prompts in productionFull prompts at every call create enormous log volume and expose sensitive instructions. Log the event (which node ran, which tool was called) not the content.
