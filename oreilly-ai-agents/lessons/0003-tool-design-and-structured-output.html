Tool Design & Structured Output

The LLM reads your tool descriptions, not you. Write them badly and the agent behaves unpredictably. Write them well and the agent becomes reliable.

Why tool design matters

Course ref: Level 2, §2.2 — Structured Outputs and §2.3 — Integrating External Tools. The principles here apply identically in Python and Node.js.

In Lesson 2 you gave the LLM a run_shell tool and it worked. But that was a toy. In a real agent — one that talks to a database, sends emails, updates records — the LLM must choose the right tool, with the right arguments, every time.

The LLM makes that choice by reading three things:

  • The tool's name
  • The tool's description
  • The tool's input schema (the JSON Schema object)

That is all it sees. Your implementation is invisible. Which means the description is your contract with the LLM — it determines when the tool gets called and how arguments are filled.

Writing good tool descriptions

The description must answer three questions the LLM silently asks before calling a tool:

  1. What does this tool do?
  2. When should I use it (vs the other tools)?
  3. What does it return?

Compare these two descriptions for a database lookup tool:

✗ Bad
'Look up user data'
✓ Good
'Look up a user record by their ID or email.
Returns { id, name, email, role, createdAt }.
Use this when you need to verify who a user is
or retrieve their account details. Do NOT use
this for searching — use search_users instead.'

The good version tells the LLM what it returns, when to prefer it, and explicitly rules out a confusion case. That last part — "Do NOT use this for searching" — is especially important when you have two similar tools.

Rule of thumb: 3–5 tools maximum per agent. Each additional tool makes the LLM's decision harder and increases the chance of the wrong tool being selected. If you have 10 tools, split into multiple agents. (Level 2, §2.3)

Anatomy of a good input schema

The input_schema is a JSON Schema object. Every property should have a type and a description. The LLM reads property descriptions to know what value to pass.

Here is a well-designed schema for a "send notification" tool:

const sendNotificationTool = {
  name: 'send_notification',
  description: 'Send a push notification to a user. Use when the task requires
    alerting a specific user. Returns { success: boolean, messageId: string }.
    Do NOT use for email — use send_email instead.',
  input_schema: {
    type: 'object',
    properties: {
      userId: {
        type: 'string',
        description: 'The UUID of the user to notify',
      },
      message: {
        type: 'string',
        description: 'The notification body. Plain text, max 140 characters.',
      },
      priority: {
        type: 'string',
        enum: ['low', 'normal', 'high'],
        description: 'Urgency level. Use "high" only for time-sensitive alerts.',
      },
    },
    required: ['userId', 'message'],  // priority is optional — defaults to 'normal'
  },
};

Notice:

  • Every property has a description — not just the tool itself
  • enum constrains the LLM to valid values, preventing hallucinated strings
  • Optional fields stay out of required
  • The tool description says what it returns

Structured output

Sometimes you don't want the LLM to call a tool — you want it to produce a structured object as its final answer. For example: extract entities from text, classify a support ticket, or triage a request into a typed response.

LLMs naturally produce prose. To get a reliable JSON object, you have two options:

MethodHowReliability
Prompt-based Tell the LLM to "respond only with JSON" in the system prompt Low — it sometimes adds prose anyway
Forced tool use Define a "response" tool and force the LLM to call it High — tool calls always produce valid schema-conforming JSON

The forced tool use trick is the standard pattern. You define a tool called respond (or format_response) that represents the output shape, then tell the API to always call it via tool_choice.

Example: extract a task from natural language

// extract-task.mjs
import Anthropic from '@anthropic-ai/sdk';

const client = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY });

// The "output schema" disguised as a tool
const respondTool = {
  name: 'respond',
  description: 'Return the extracted task as structured data',
  input_schema: {
    type: 'object',
    properties: {
      title: {
        type: 'string',
        description: 'Short task title, max 8 words',
      },
      description: {
        type: 'string',
        description: 'Full task description in one sentence',
      },
      priority: {
        type: 'string',
        enum: ['low', 'medium', 'high'],
        description: 'Inferred urgency from the user\'s language',
      },
      dueDate: {
        type: 'string',
        description: 'ISO 8601 date if mentioned, otherwise null',
        nullable: true,
      },
    },
    required: ['title', 'description', 'priority'],
  },
};

async function extractTask(userInput) {
  const response = await client.messages.create({
    model: 'claude-haiku-4-5-20251001',
    max_tokens: 512,
    system: 'You are a task extraction assistant. Extract the task from the user\'s message.',
    tools: [respondTool],
    tool_choice: { type: 'tool', name: 'respond' }, // ← forces the LLM to call this tool
    messages: [{ role: 'user', content: userInput }],
  });

  // The tool call input IS the structured output
  const toolCall = response.content.find(b => b.type === 'tool_use');
  return toolCall.input; // { title, description, priority, dueDate }
}

const result = await extractTask(
  'Hey, can you remind me to send the Q3 report to Sarah by Friday? It\'s pretty urgent.'
);

console.log(JSON.stringify(result, null, 2));

Expected output:

Terminal output
{ "title": "Send Q3 report to Sarah", "description": "Send the Q3 report to Sarah by Friday as it is urgent.", "priority": "high", "dueDate": "2026-06-20" }

No JSON parsing, no regex, no try-catch around JSON.parse. The tool call always produces schema-conforming input — guaranteed by the API.

Validation with Zod (the TypeScript equivalent of Pydantic)

The course uses Python's Pydantic for validation. In Node.js/TypeScript, Zod is the direct equivalent. Same idea: define a schema, validate at runtime, get typed output.

The API guarantees the shape matches your schema, but doesn't give you TypeScript types. Use Zod to validate and get full type inference: 

npm install zod
import { z } from 'zod';

// Define the shape once with Zod
const TaskSchema = z.object({
  title:       z.string().max(60),
  description: z.string(),
  priority:    z.enum(['low', 'medium', 'high']),
  dueDate:     z.string().nullable(),
});

type Task = z.infer<typeof TaskSchema>;

// After getting toolCall.input from the API:
const task: Task = TaskSchema.parse(toolCall.input);
// task is now fully typed — autocomplete works, type errors caught at compile time

In a NestJS service, you'd also use a Zod schema (or a class-validator DTO) to validate the output before passing it downstream — exactly the same pattern as validating a request body.

Tool design checklist

Before adding a tool to an agent, run through this:

CheckWhy
Name is a clear verb-nounsend_email not email or mailer
Description says what it returnsLLM needs to know what data it gets back
Description says when not to use itPrevents confusion with similar tools
Every property has a descriptionLLM reads these to decide argument values
Enums used for finite valid valuesPrevents hallucinated strings like "urgent"
Optional fields excluded from requiredLLM won't be forced to invent values
Total tools per agent ≤ 5More tools = slower + less reliable selection

▶
⚡ Engineering tensions
Tool granularity vs. LLM decision load—Fine-grained tools (one operation each) give precise control but require the LLM to make more routing decisions per task, increasing error rates. Coarse-grained tools reduce decisions but are harder to validate. 3–5 focused tools is the practical sweet spot.
Tool reliability vs. agent resilience—A tool that always succeeds hides brittle assumptions. A tool that returns structured errors lets the agent reason about failures. Designing tools to fail gracefully is harder to build but produces dramatically more resilient agents.
MCP interoperability vs. protocol overhead—MCP gives you M+N integrations instead of M×N. But MCP adds protocol overhead (subprocess communication, schema negotiation) that matters in latency-sensitive applications. For 1–2 tools, direct integration is simpler and faster.
Strict schema vs. LLM flexibility—A Pydantic schema with tight validation prevents invalid values but creates a deployment coordination problem when the valid values change — you must update schema and prompt simultaneously.
Structured output overhead vs. reliability—with_structured_output() adds an internal tool-calling step and sometimes a retry — adds 100–300ms. For high-throughput pipelines, this compounds. Some teams use regex parsing for simple cases; structured output for complex schemas.
Tool count vs. selection accuracy—Above 7–10 tools, LLM tool selection accuracy degrades. The model starts confusing similar tools. This is a hard architectural constraint: if you need more than 5–7 tools, you need multiple agents.
Error handling strategy: return vs. raise—Returning error dicts lets the LLM recover gracefully but requires the LLM to understand and act on errors. Raising exceptions crashes the loop but makes failures explicit. Return for recoverable errors, raise for unrecoverable.
💬 Staff-level questions
Q1
You have a tool that takes 2–5 seconds to execute. How does this affect your agent architecture, user experience design, and error handling strategy?
Steer: A slow tool changes the math on parallelism, user feedback, and retry cost.
Architecture: if the tool is called multiple times per run, parallelize calls using asyncio.gather — call it simultaneously for different inputs rather than sequentially. Add a tool-level cache for identical inputs within a session (a slow tool called twice with the same input should return the cached result immediately). UX: stream progress indicators — 'Checking inventory... (this may take a few seconds)' rather than a silent spinner. For chat interfaces, stream intermediate status updates from the agent. Error handling: a 5-second timeout on a tool that sometimes takes 5+ seconds means frequent timeout errors — set timeouts at 2× the P95 execution time, not the mean. On timeout: return an error dict (not an exception), let the LLM decide whether to retry or proceed without this data.
Q2
An LLM keeps calling the wrong tool for a specific query pattern. Walk through the systematic debugging process you'd use to fix it without just rewriting the prompt.
Steer: Wrong tool selection is usually a docstring problem or a tool similarity problem. Diagnose before prescribing.
Step 1: Log the full context sent to the LLM when the wrong tool is selected. What did the model see? Step 2: Check if the two tools (correct and incorrect) have similar descriptions. If so, the LLM cannot distinguish them — make the descriptions more discriminative by adding 'use this tool when X, NOT when Y.' Step 3: Check if the query pattern contains words that appear in the wrong tool's description but not the right one. Update the right tool's description to explicitly address this pattern. Step 4: If the model consistently calls tool A when tool B is needed, add a few-shot example to the system prompt showing this exact query type routing to tool B. Step 5: If the problem persists, add a routing pre-processor: a cheap LLM call that classifies query intent and constrains which tools are available for this query type.
Q3
Design a tool permission system where different users can invoke different subsets of tools. How does this interact with the system prompt and agent decision-making?
Steer: Permissions live at the tool layer, not the prompt layer. How do you ensure the LLM only knows about tools it's allowed to use?
Pattern: at request time, load the user's permission set. Filter the full tool list to only the tools that user is permitted to call. Pass only the permitted tools to llm.bind_tools() — the LLM never sees tools it can't use, so it can never try to call them. The system prompt says 'use the available tools' without listing them explicitly (the tools are passed via the tools parameter, not the prompt). This way, there's no prompt injection path to accessing forbidden tools: the tool schema simply isn't in the LLM's context. Additionally: validate at the tool execution layer that the requesting user has permission to call this tool — defense in depth in case the tool schema filtering has a bug.
Q4
When should a tool call the LLM internally vs. returning raw results for the agent to process? What are the tradeoffs?
Steer: A tool that calls an LLM internally is itself an agent. When is this the right pattern vs. an antipattern?
Tool calling LLM internally is appropriate when: the tool's purpose is inherently language-based (e.g., a 'summarize_document' tool), the processing is stable and the same every time (not requiring the outer agent's context), and you want to hide complexity from the outer agent's context window. It's an antipattern when: the tool's LLM call uses context that the outer agent has but the tool doesn't — this requires passing a large context into the tool, making the tool tightly coupled to the agent. Also antipattern when: the tool's output needs to feed back into the agent's reasoning in a nuanced way — the outer agent should see the raw data and reason about it. Rule of thumb: tools should do deterministic work. If the work requires judgment or context from the broader conversation, it belongs in the agent, not the tool.
Q5
How do you version tool APIs so that changes to a tool don't break agents in production?
Steer: Tool APIs are contracts between the LLM and the tool implementation. Treat them like any other API contract.
Treat tools like REST APIs: (1) Version tool names explicitly (search_inventory_v2) or use parameter versioning. (2) Never change a tool's parameter names or types without a migration — the LLM has learned to call the tool with specific parameter names from the docstring. (3) Deprecate, don't delete — run old and new versions side by side with the old version logging a warning when called. (4) Run LLM regression tests after any tool change: does the agent still call the tool correctly for the 20 most common query patterns? (5) Treat the docstring as part of the API contract — changes to the docstring can change LLM behavior even if the code is unchanged. Version control docstrings alongside code.
Q6
A tool calls an external API that occasionally returns stale data (cached at the API provider for 5 minutes). How do you handle this in your agent architecture?
Steer: Stale data is a correctness problem that looks like a performance problem. The agent may make decisions based on data that was accurate 5 minutes ago.
Handle at three layers: (1) Tool level: include a data_freshness field in the return value: {data: ..., cached_at: '2024-01-15T10:30:00Z', max_age_seconds: 300}. (2) Prompt level: instruct the agent: 'When a tool returns cached data, include the cache age in your response and caveat time-sensitive facts.' (3) Application level: for decisions where staleness matters (e.g., inventory checks before committing an order), add a freshness check: if cached_at > 4 minutes ago, call a cache-bypass endpoint (if available) or add a caveat to the final output. Track cache hit rates in your observability system — high cache hit rates may indicate the external API is having problems.
Q7
Design a structured output schema for a classifier that needs to handle documents that don't fit any known category.
Steer: Closed-world classification schemas force the LLM to pick a wrong answer rather than admitting uncertainty.
Add an explicit escape hatch: category: Literal['billing', 'technical', 'refund', 'other']. When other is selected, require additional context: reasoning: str — why no category fits, suggested_category: Optional[str] — what new category would fit, confidence: Literal['high', 'medium', 'low'] — how uncertain. The application layer handles 'other': route to human review, log for analysis (the 'other' category distribution tells you what new categories to add), and use it as a training signal for the classifier. Never ship a schema without an 'other' or 'unknown' option — unknown inputs are a certainty in production.
Q8
How do you version structured output schemas in a multi-service architecture where different services consume the output?
Steer: Schema changes are breaking changes for consumers. How do you manage this safely?
Treat output schemas like REST API versions: (1) Additive changes (new optional fields) are safe — existing consumers ignore unknown fields if they use a permissive parser. (2) Removing or renaming fields is a breaking change — requires versioning. Version naming: ClassificationV1, ClassificationV2. (3) Maintain both versions simultaneously during transition. Producer supports V1 and V2. Consumers migrate to V2 at their own pace. (4) Deprecate V1 after all consumers have migrated. (5) Use a schema registry (or even just a shared package) that all services import the Pydantic models from — single source of truth for schema definition. A schema change PR requires updating the shared package and identifying all downstream consumers. Version bump in the shared package is the signal to update.
Q9
Structured output validation fails at 2am in production. The LLM keeps returning values not in your Literal type. What's your recovery path?
Steer: You need a short-term fix (keep production running) and a medium-term fix (prevent recurrence).
Short-term recovery: (1) Catch the ValidationError in your agent wrapper. (2) Add a fallback: if structured output fails 3 times, fall back to string output with a best-effort parse. Log the fallback prominently. (3) Set state['status'] = 'degraded' and continue with a safe default (route to the most conservative handler, not the most appropriate one). Medium-term fix: (1) Log the raw LLM output when validation fails — what did it actually return? (2) Common cause: model returned a value that's semantically correct but not in your Literal (e.g., 'urgent' vs. 'critical'). Fix: add synonyms to the schema or update the prompt with explicit examples of what 'critical' looks like. (3) Another common cause: model returned a value in a different language. Add language=Literal['en'] to your schema if multilingual inputs are possible. Prevention: add a schema validation test in CI that runs 20 representative queries and verifies all return valid Pydantic objects.
Q10
How do you use structured output to make agent debugging easier?
Steer: Structured output produces typed, predictable data. How does this change your debugging workflow?
Structured output dramatically improves debugging because: (1) You know exactly what fields the LLM filled in and what values it chose — no string parsing required to understand the decision. (2) Validation failures are immediate and explicit (ValidationError with the exact field that failed) rather than silent (a string parse that produces garbage). (3) You can log the full structured object as JSON without ambiguity. (4) In debugging: filter logs by field values — 'show me all runs where priority=critical that routed to standard_handler.' (5) For A/B testing: compare the distribution of output field values between model versions — 'did the new model classify more items as urgent?' This would be impossible with free-text output. Best practice: define structured output schemas for every decision node in your agent, even internal ones. The schema documents the agent's reasoning at each step.
Q11
When should you NOT use structured output, even when it seems like it would help?
Steer: Structured output is a constraint. Constraints have costs.
Avoid structured output when: (1) The output is inherently free-form and its value lies in the LLM's language quality (creative writing, complex explanations, conversational responses). Forcing into a schema degrades quality and adds latency for no benefit. (2) The output structure is highly variable and you would need a very complex schema with many optional fields — the schema itself becomes a maintenance burden. Use a simpler approach (e.g., just extract key fields with regex) or use free-form output with a separate extraction pass. (3) You're using a weak model that struggles to reliably produce valid schema outputs — you'll spend more time retrying failed validations than you'd spend parsing strings. (4) Latency is extremely critical (<100ms target) — the structured output mechanism adds a step. Use a simple Literal choice with a routing prompt instead.
Q12
Two tools do similar things (search_products and browse_catalog). The LLM keeps picking the wrong one. What is your systematic fix?
Steer: The LLM reads docstrings to decide. The docstrings are probably too similar.
Step 1: Make the docstrings discriminative. Don't describe what each tool does — describe when to use each one vs. the other. search_products docstring: 'Use when the user provides specific product attributes (name, SKU, category, price range). NOT for browsing.' browse_catalog docstring: 'Use when the user wants to explore what's available without specific criteria. NOT for searching by attribute.' Step 2: Add negative examples to the system prompt: 'When the user says "show me all products" → browse_catalog. When the user says "find product SKU-123" → search_products.' Step 3: If confusion persists, merge them into one tool with a mode parameter: search_or_browse(mode: Literal['search', 'browse'], query: Optional[str]). Reducing decision count reduces error rate.
Q13
Design a tool that interacts with a rate-limited external API. How do you handle rate limits gracefully within the tool without breaking the agent loop?
Steer: Rate limits are predictable, recoverable errors. The tool should handle them internally, not propagate them as failures.
Inside the tool: (1) Catch the 429 response. (2) Read the Retry-After header if present. (3) sleep(retry_after + jitter) inside the tool — not in the agent loop. (4) Retry up to 3 times with exponential backoff within the tool. (5) If all retries exhausted: return {'status': 'rate_limited', 'message': 'External API rate limit exceeded after 3 retries. Try again in 60 seconds.', 'retry_after': 60}. The agent receives a structured error it can reason about. It might respond: 'I'm unable to check inventory right now due to an external API rate limit. I'll note this and you can try again shortly.' The agent loop never sees a 429 exception — the tool handles it internally.
Q14
A tool requires authentication credentials. Design the credential management strategy that doesn't expose secrets to the LLM context or logs.
Steer: Credentials must reach the tool implementation but never touch the LLM's context window or any logs.
Credentials management: (1) Store credentials in environment variables or a secrets manager (AWS Secrets Manager, HashiCorp Vault). Never in code. (2) Load credentials at application startup, not at call time. (3) Inject credentials into the tool function via closure or dependency injection — the tool function has access to the credential object without it being passed through the agent's state or context. Example: def make_inventory_tool(api_key: str): def check_inventory(product_id: str) -> dict: # api_key captured in closure, never in context return client.get(product_id, auth=api_key). (4) Logging: mask credentials in all logs. Add a log sanitizer that replaces any string matching the credential pattern with [REDACTED]. (5) The LLM context never contains credentials — it sees only the tool name, parameters, and results. Credentials flow through a separate channel.
Q15
How do you test that a tool correctly handles every error mode — network errors, authentication errors, not-found errors, rate limits?
Steer: Testing error paths requires mocking the external service to return specific error responses.
Mock-based testing: (1) Use unittest.mock.patch to replace the external API client with a mock that returns specific responses. (2) Test each error class: mock.return_value = Mock(status_code=429, headers={'Retry-After': '30'}) → verify tool returns {status: 'rate_limited', retry_after: 30}. mock.return_value = Mock(status_code=404) → verify tool returns {status: 'not_found', message: '...'}. mock.side_effect = ConnectionError() → verify tool returns {status: 'network_error', ...}. (3) Integration tests (test against a test API environment, not mocks) verify that the mock behavior matches real API behavior. (4) Property-based test: any response from the external API that is not a 200 should result in a structured error dict, never an exception propagating to the agent loop. Write a test that exercises 20 non-200 status codes and verifies this invariant.
Q16
What makes a good tool docstring vs. a bad one? Rewrite this bad example: 'Gets product data.'
Steer: The docstring is the instruction the LLM reads to decide when and how to call the tool. Write it for an LLM, not a human developer.
Bad: 'Gets product data.' — tells the LLM nothing about when to use it, what to pass, or what it returns. Good rewrite: 'Retrieves detailed product information from the inventory system. Use when the user asks about product specifications, availability, pricing, or description for a specific product. Requires a product_id (alphanumeric, e.g., "SKU-1234"). Returns: {name, description, price, quantity_in_stock, category}. NOT for searching across multiple products — use search_products instead. Example: product_id="SKU-1234" to look up the Widget Pro.' Key elements: when to use, when NOT to use, what parameters mean with examples, what the return value contains. The docstring should answer every question the LLM needs to call this tool correctly without trial and error.
🔴 Production pitfalls
Tools that succeed silently when they should failA database update returns {status: 'ok'} even when 0 rows were updated (no exception thrown). The agent believes it succeeded. Design tools to distinguish 'executed without error' from 'produced the intended outcome' — check affected row counts, verify side effects, return explicit success indicators.
Docstring driftA tool's behavior changes but the docstring is not updated. The LLM reads the old description and misuses the tool. Treat tool docstrings with the same rigor as API contracts — version them, review changes, and run behavioral regression tests after updates.
More than 7 tools in one agentAbove 7–10 tools, LLM tool selection accuracy degrades noticeably. The model starts confusing similar tools. This is a hard architectural constraint: if you need more than 5–7 tools, split into multiple specialized agents.
Missing the 'unknown' caseA classification schema with Literal['billing', 'technical', 'refund'] has no escape hatch for inputs that don't fit. The LLM will force-fit every input into one of three categories. Always include an 'other' or 'unknown' option and handle it explicitly downstream.
Over-engineering the schemaA 20-field schema with 5 nested objects for a 3-way classification task. The LLM spends tokens on schema compliance rather than accurate classification. Start with the minimum fields you actually use downstream. Add fields only when there's a specific use case.
Stateful tools in stateless agentsA tool that modifies external state is not idempotent. If the agent retries after a network timeout, it may call the tool twice — sending the email twice, placing the order twice. Design write tools with idempotency keys (include a unique request_id in every write call) or check-before-write.
Tools that raise unhandled exceptionsAn unhandled exception in a tool propagates to the agent loop and crashes it. Every tool must catch all exceptions and return structured error dicts. No exception should ever escape a production tool.
