Memory & Conversation State

Every agent you have built so far forgets everything when the process ends. This lesson fixes that — and shows you which kind of memory to reach for when.

Three kinds of memory

Course ref: Level 3, §3.10 — Conversation History and §3.11 — Semantic Memory.
Type 1
In-context
The messages array. Lives in RAM. Fast. Bounded by the context window. Gone when the process exits.
Type 2
Persistent
Messages saved to a DB (Postgres, Redis, file). Survives restarts. Loaded by thread ID. Backbone of multi-session chat.
Type 3
Semantic
Facts stored as vector embeddings. Retrieved by meaning, not exact key. Cross-session knowledge that scales indefinitely.

You have been using Type 1 in every lesson so far. This lesson adds Type 2. Type 3 (vector memory) is Lesson 6 — once you have the foundation.

The context window is not infinite

Every API call sends the full messages array. That means cost and latency grow with every turn. Two practical limits to know:

ModelContext windowPractical conversation limit
claude-haiku-4-5200k tokens~500 back-and-forth turns
claude-sonnet-4-6200k tokens~500 turns, higher quality

For most agents that limit is irrelevant. But cost matters — sending 400 old messages on every call burns tokens you do not need. The fix: trim the oldest messages once you exceed a threshold, or keep a rolling summary.

Conversation threading

A thread is one isolated conversation — like a single chat window. Each thread has a unique ID. On every request you load the thread, run the agent, then save.

Request + threadId
→
Load messages
→
Run agent
→
Save messages
→
Return response

In NestJS terms: the thread store is a repository. The agent service loads by threadId, runs the loop, persists the result. No new concepts — just a data-access pattern you already know.

Build it: stateful agent with file-based persistence

We use JSON files per thread — no external dependencies for now. In production, swap loadThread and saveThread for a Postgres repository. The agent code stays identical. 

// stateful-agent.mjs
// Usage:
//   node --env-file=.env stateful-agent.mjs <threadId> "<message>"
//
// Try this sequence:
//   node --env-file=.env stateful-agent.mjs abc123 "My name is Derese"
//   node --env-file=.env stateful-agent.mjs abc123 "What is my name?"   (new process — still remembers)
//   node --env-file=.env stateful-agent.mjs xyz999 "What is my name?"   (different thread — blank)

import Anthropic from '@anthropic-ai/sdk';
import { readFileSync, writeFileSync, existsSync, mkdirSync } from 'fs';

const client = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY });
mkdirSync('./threads', { recursive: true });

// ── THREAD STORE (swap this layer for Postgres/Redis in production) ───────────

function loadThread(threadId) {
  const path = `./threads/${threadId}.json`;
  return existsSync(path) ? JSON.parse(readFileSync(path, 'utf8')) : [];
}

function saveThread(threadId, messages) {
  writeFileSync(`./threads/${threadId}.json`, JSON.stringify(messages, null, 2));
}

// ── CONTEXT TRIMMING (keep last N turns to control token cost) ────────────────

function trimToLastN(messages, n = 20) {
  return messages.length <= n ? messages : messages.slice(-n);
}

// ── AGENT ─────────────────────────────────────────────────────────────────────

async function chat(threadId, userMessage) {
  const history = loadThread(threadId);

  console.log(`[thread:${threadId}] ${history.length} prior messages`);

  const messages = [
    ...trimToLastN(history),           // past context, trimmed
    { role: 'user', content: userMessage }, // new turn
  ];

  const response = await client.messages.create({
    model: 'claude-haiku-4-5-20251001',
    max_tokens: 1024,
    system: 'You are a helpful assistant with memory of this conversation.',
    messages,
  });

  const reply = response.content
    .filter(b => b.type === 'text')
    .map(b => b.text)
    .join('');

  console.log(`User: ${userMessage}`);
  console.log(`Assistant: ${reply}\n`);

  // Save the FULL history (not trimmed) — trim only what we SEND to the API
  saveThread(threadId, [
    ...history,
    { role: 'user', content: userMessage },
    { role: 'assistant', content: reply },
  ]);

  return reply;
}

// ── ENTRYPOINT ────────────────────────────────────────────────────────────────

const [,, threadId, ...rest] = process.argv;
if (!threadId || !rest.length) {
  console.log('Usage: node stateful-agent.mjs <threadId> "<message>"');
  process.exit(1);
}
await chat(threadId, rest.join(' '));

Run it — across separate processes

node --env-file=.env stateful-agent.mjs abc123 "My name is Derese, I build NestJS apps"
node --env-file=.env stateful-agent.mjs abc123 "What do you know about me?"
node --env-file=.env stateful-agent.mjs xyz999 "What do you know about me?"
Expected (second call)
[thread:abc123] 2 prior messages User: What do you know about me? Assistant: You told me your name is Derese and that you build NestJS applications.
Expected (third call — different thread)
[thread:xyz999] 0 prior messages User: What do you know about me? Assistant: I don't have any information about you yet. Feel free to share!

The thread files appear under ./threads/. Open one — you'll see the raw messages array as JSON. That is the agent's long-term memory, fully inspectable and editable.

The trim vs save distinction

Critical pattern. Trim what you send to the API to control cost. Save the full history to disk so you never lose turns. These two things are independent.

The code above saves to history (the full array) but sends trimToLastN(history) to the API. This means:

  • Old turns are preserved on disk for auditing or replay
  • The API only pays for the last 20 turns each call
  • You can increase the trim window any time without data loss

When to add semantic memory (Type 3)

Persistent threads solve the session problem but not the scale problem. If a user has 500 past conversations, you cannot load all 10,000 messages into context. That is when you need semantic memory:

SituationUse
Single ongoing conversationIn-context (messages array)
Returning users across sessionsPersistent thread (DB)
Long history — retrieve only relevant past factsSemantic / vector memory
Shared knowledge base across many usersSemantic / vector memory

Semantic memory (embeddings + vector search) is Lesson 6. You need the threading foundation first.

⚡ Engineering tensions
Memory freshness vs. retrieval latency—Semantic search adds 50–200ms per query. For a user waiting for a response, this is noticeable. You can pre-fetch memory in parallel with other operations, cache recent memories, or accept the latency. Each choice has engineering cost.
Memory precision vs. recall—High-k retrieval (many memories) reduces missing relevant context but floods the prompt with noise. Low-k keeps the context clean but risks missing the critical memory. k=3–5 is the typical starting point; tune empirically for your domain.
Hotpath vs. background memory writing—Writing memory synchronously means it's available for the next turn but adds response latency. Writing asynchronously removes the latency hit but means the agent may not remember something it just learned in the previous turn. Choose based on whether you need 'instant recall' or 'eventual consistency.'
Stateful chatbot vs. stateless architecture—A stateful chatbot with checkpointing lets users resume conversations but adds a dependency. A stateless chatbot passes conversation history in the request payload — simpler but puts state management on the client.
add_messages deduplication vs. custom message handling—add_messages deduplicates by message ID. If you construct messages with the same ID for testing, deduplication will silently drop them. Understand the reducer's semantics before relying on it.
💬 Staff-level questions
Q1
Design a memory system for a multi-tenant SaaS where User A's memories must never surface in User B's session, and memories must be scoped by workspace.
Steer: Isolation is a namespace problem. What keys do you use, and where do you enforce the filtering?
Use hierarchical namespacing: namespace = (tenant_id, workspace_id, 'memories'). Every write to the memory store includes these namespace components. Every read filters by the same namespace — physically impossible to retrieve cross-tenant memories because the vector search is scoped to the namespace. At the application layer: extract tenant_id and workspace_id from the authenticated request context, never from user-provided input. Validate at both the write and read path. In LangGraph's InMemoryStore, the namespace parameter enforces this isolation. For production (Pinecone, Weaviate, pgvector), add a metadata filter: {tenant_id: X, workspace_id: Y} to every similarity search. Audit: log every memory write and read with the namespace — if you ever see a cross-namespace access in logs, that's a critical security incident.
Q2
How do you handle conflicting memories? User stored 'prefers Python' in January and 'now works in Go' in March. How do you resolve at retrieval time?
Steer: Conflicts are temporal — the newer one is usually correct. But 'usually' is not 'always.'
Three strategies: (1) Recency-weighted retrieval: store a timestamp with every memory. When two memories conflict, surface the newer one with higher priority. Include timestamps in the retrieved context so the LLM can reason about recency: 'User prefers Python (Jan 2024), User now works in Go (Mar 2024).' (2) Update-on-conflict: when writing a new memory, check if it contradicts an existing one (LLM-based conflict detection). If yes, update the existing memory rather than adding a duplicate. Store the change history. (3) Explicit contradiction flag: mark conflicting memories and surface both with a note: 'There is a conflict in user preferences. The more recent preference is Go.' Let the LLM handle resolution contextually. In practice: use recency-weighting as default, add conflict detection for high-value memory types (user preferences, contact info).
Q3
What is your strategy for memory maintenance at scale? When does pruning become necessary, and what is the decision rule?
Steer: Memory stores that only grow eventually degrade retrieval quality and increase cost. Pruning needs a principled rule, not ad-hoc deletion.
Pruning becomes necessary when: (1) Retrieval latency increases beyond your SLA (the index is too large to search efficiently), (2) Stale memories are surfacing in top-k results and affecting output quality, (3) Storage cost exceeds budget. Decision rule for what to prune: importance score × recency score. Importance: was this memory ever retrieved and used? Track retrieval frequency. Recency: how old is this memory? Apply exponential decay. Score = retrieval_count × exp(-age_days / half_life). Prune memories below a threshold score. For user-facing systems: add a TTL to low-confidence or factual memories (facts change). Keep procedural memories (the user's workflow preferences) indefinitely unless explicitly updated. Never delete the 5 most recently accessed memories regardless of score.
Q4
Design an evaluation framework for memory quality. How do you measure whether the memory system is improving agent responses?
Steer: Memory impact is an attribution problem — how do you know whether the retrieved memory changed the response?
A/B evaluation: split traffic 50/50 — treatment group receives retrieved memories in context, control group does not. Use LLM-as-judge to rate both responses on relevance, personalization, and accuracy. Memory lift = quality_with_memory - quality_without_memory. Also measure: (1) Memory relevance rate — what % of retrieved memories are actually relevant to the query? Rate with LLM-as-judge. (2) Memory usage rate — what % of the time does the LLM actually reference the retrieved memory in its response? (3) Personalization score — does the response address the user's known preferences? Track with a rubric. (4) Retrieval cost vs. quality lift — is the 150ms retrieval latency and token cost justified by the quality improvement? If memory lift is <5% and cost is high, simplify.
Q5
When should you use vector store (semantic) memory vs. key-value (exact lookup) vs. SQL (structured query) vs. knowledge graph (entity relationships)?
Steer: Each storage type has a query pattern it excels at. Match the query pattern to the storage type.
Vector store: when you need 'find memories semantically related to this current context' — fuzzy, meaning-based retrieval. Use for: user preferences, past experiences, anything where exact matching fails. Key-value: when you need 'fetch this specific fact by ID instantly' — low latency, exact match. Use for: user timezone, subscription tier, last session timestamp — structured facts with known keys. SQL: when you need 'find all memories where topic=X and date>Y' — structured, filterable, aggregatable. Use for: interaction history, event logs, auditable records. Knowledge graph: when you need 'traverse relationships between entities' — user works at company X, company X uses technology Y, technology Y has known vulnerability Z. Use for: rich entity relationship modeling where the connections matter as much as the facts. Most production systems use 2–3 of these in combination.
Q6
How does memory change the failure modes of an agent compared to a memoryless one? What new bugs does it introduce?
Steer: Memory adds a new data source that can be wrong, outdated, or irrelevant. What does the agent do when memory misleads it?
New failure modes: (1) Memory poisoning — a bad interaction writes incorrect information to memory. The agent then retrieves and acts on wrong information indefinitely. Mitigate: add a confidence score to memories, require multiple consistent signals before storing high-confidence memories. (2) Memory hallucination — the LLM 'remembers' something that's actually not in the retrieved memories. The retrieved context acts as a false anchor. Mitigate: instruct the agent 'only reference facts that appear in the provided memories' and add output validation. (3) Stale memory relevance — a retrieved memory was accurate 6 months ago and is now misleading. Mitigate: include memory timestamps in context and instruct: 'memories older than 30 days should be treated as potentially outdated.' (4) Memory selection bias — the retriever consistently retrieves certain types of memories over others. The agent develops a skewed view of the user. Audit retrieval diversity regularly.
Q7
How do you implement conversation summarization when message history grows too long?
Steer: The history needs to shrink without losing important context.
Add a check_and_trim_history node that runs before the main assistant node: if token_count(messages) > threshold (e.g., 75% of context window): run a summarization LLM call: 'Summarize the key facts and decisions from this conversation history in 200 words.' Replace old messages with: [HumanMessage('Previous conversation summary: {summary}'), ...last 5 messages]. The last 5 messages are kept verbatim — they're most relevant and the LLM needs them for continuity. The summary captures key facts and decisions without verbatim dialogue. Track: how often summarization triggers, token count before and after, response quality on queries that reference summarized content. If quality degrades on summarized queries, increase the number of verbatim messages retained.
Q8
Design a multi-user chatbot where different users can share a conversation thread (team chat with AI). How do you design state and thread IDs?
Steer: Multiple users in one thread means messages need user attribution, and thread IDs must be team-scoped.
Thread ID: team_{team_id}_channel_{channel_id} — scoped to the shared context, not per-user. State adds: sender_user_id to each message metadata. Messages: use add_messages but each message includes {role: 'human', content: '...', metadata: {user_id: X, username: 'Alice'}}. The assistant node sees all messages with attribution. System prompt adapts: 'This is a team conversation. Multiple users may ask questions. Address each user by name when responding to them specifically. When summarizing, note which user provided which information.' Access control: validate that the requesting user is a member of team_{team_id} before allowing reads or writes to the thread. The thread is shared; access is controlled by team membership, not individual thread IDs.
Q9
What does tools_condition check, and how does it create the agent loop?
Steer: tools_condition is the routing function at the heart of the chatbot loop. Trace exactly what it reads and what it returns.
tools_condition reads the last message in state.messages. If the last message is an AIMessage with tool_calls (the LLM decided to use a tool), it returns 'tools' → routes to the ToolNode. If the last message is an AIMessage without tool_calls (the LLM gave a final answer), it returns END → terminates. This creates the loop: assistant_node → tools_condition → (if tool_calls) tools_node → assistant_node (the tool result becomes a new message, prompting the assistant to continue). The loop terminates when the assistant produces a response without requesting any tools. The key insight: the 'loop' is not an explicit while loop in your code — it's an emergent property of the graph's conditional edge routing. tools_condition is the termination condition.
🔴 Production pitfalls
Memory without forgettingA memory store that only ever grows eventually surfaces outdated, contradictory memories. After 6 months, early preferences may actively mislead. Implement memory decay, importance scoring, or explicit update mechanisms from day one.
Namespace collision in multi-tenant systemsUsing flat keys (memory_123) instead of hierarchical namespacing (user_A/workspace_1/memory_123) means memories can bleed across tenants. Always namespace by user_id and context_type from day one — retrofitting is painful.
Synchronous memory retrieval blocking responsesCalling the memory store synchronously before every response adds 150–300ms to P50 latency. Parallelize: start memory retrieval at the same time as other initialization steps using asyncio.gather, not sequentially.
Unbounded message historyadd_messages accumulates all messages forever. After a long conversation, the messages list consumes the entire context window. Implement sliding window trimming or summarization for long-running sessions.
Thread ID collisionUsing simple IDs across a multi-tenant system will eventually collide. Always namespace: customer_A_session_1, never just session_1.
