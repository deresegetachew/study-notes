Multi-Agent Systems

One agent with 15 tools is slow, unreliable, and hard to debug. Multi-agent systems fix this by splitting expertise across specialised agents coordinated by a supervisor.

Why single agents hit a ceiling

Course ref: Level 4, §4.2 — Supervisor Systems and §4.3 — Swarm Architecture.

In lesson 3 you learned to keep tools to 3–5 per agent. But real products need more capability than that. A customer support agent might need to handle billing queries, technical troubleshooting, account management, and refund processing — each a domain in itself.

Cramming all of that into one agent causes two problems:

  • Decision quality drops. The more tools an LLM must choose between, the more often it picks the wrong one.
  • Debugging becomes hard. When something goes wrong you cannot tell which "role" caused it.

The solution is the same one you'd use in a NestJS codebase: split by responsibility.

Two patterns: supervisor vs swarm

Supervisor (use this first)
One coordinator agent routes each request to the right specialist. The supervisor decides who handles what.

Best for: known workflow steps, predictable routing, governance and auditability required.
Swarm (for later)
Agents hand off to each other peer-to-peer. No central coordinator — any agent can decide to pass the task on.

Best for: unpredictable routing, speed-critical flows, fluid multi-step collaboration.
Start with supervisor. It is easier to reason about, easier to test, and easier to debug. Swarms are powerful but their emergent behaviour is harder to predict. (Level 4, §4.3)

The supervisor does not answer the user directly — it decides which specialist to call. Each specialist has a tight set of tools and a focused system prompt. The supervisor collects the specialist's answer and returns it.

Build it: customer support supervisor in Node.js

Two specialists (billing, tech_support) and one supervisor that routes between them. The supervisor uses structured output (Lesson 3 pattern) to make its routing decision reliably.

multi-agent.mjs
// multi-agent.mjs
// node --env-file=.env multi-agent.mjs

import Anthropic from '@anthropic-ai/sdk';

const client = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY });

// ── SPECIALIST AGENTS ─────────────────────────────────────────────────────────
// Each agent has: a system prompt defining its role + a small tool set.
// 3-5 tools each, tightly scoped. They know nothing about each other.

const specialists = {
  billing: {
    system: `You are a billing specialist. You handle invoices, charges, refunds,
and payment methods. You only deal with financial matters.
If the user's issue is not billing-related, say so clearly.`,
    tools: [
      {
        name: 'get_invoice',
        description: 'Look up an invoice by ID. Returns invoice details including amount, status, and line items.',
        input_schema: {
          type: 'object',
          properties: { invoice_id: { type: 'string', description: 'The invoice ID, e.g. INV-1234' } },
          required: ['invoice_id'],
        },
      },
      {
        name: 'issue_refund',
        description: 'Issue a refund for an invoice. Returns confirmation ID.',
        input_schema: {
          type: 'object',
          properties: {
            invoice_id: { type: 'string', description: 'The invoice to refund' },
            reason: { type: 'string', description: 'Reason for the refund' },
          },
          required: ['invoice_id', 'reason'],
        },
      },
    ],
  },

  tech_support: {
    system: `You are a technical support specialist. You diagnose software bugs,
connectivity issues, and product errors. You do not handle billing or accounts.
If the issue is not technical, say so clearly.`,
    tools: [
      {
        name: 'check_system_status',
        description: 'Check whether a given service or system component is operational. Returns status: ok | degraded | down.',
        input_schema: {
          type: 'object',
          properties: { service: { type: 'string', enum: ['api', 'dashboard', 'webhooks'], description: 'The service to check' } },
          required: ['service'],
        },
      },
      {
        name: 'create_support_ticket',
        description: 'Create a support ticket for an issue that needs engineer investigation. Returns ticket ID.',
        input_schema: {
          type: 'object',
          properties: {
            summary: { type: 'string', description: 'One-line issue summary' },
            severity: { type: 'string', enum: ['low', 'medium', 'high'], description: 'Impact severity' },
          },
          required: ['summary', 'severity'],
        },
      },
    ],
  },
};

// ── MOCK TOOL EXECUTION ───────────────────────────────────────────────────────

function executeTool(name, input) {
  const mocks = {
    get_invoice: () => JSON.stringify({ id: input.invoice_id, amount: 99.00, status: 'paid', date: '2026-06-01' }),
    issue_refund: () => JSON.stringify({ confirmation: 'REF-9921', status: 'approved' }),
    check_system_status: () => JSON.stringify({ service: input.service, status: 'ok' }),
    create_support_ticket: () => JSON.stringify({ ticket_id: 'TKT-4457', status: 'created' }),
  };
  return mocks[name]?.() ?? 'Unknown tool';
}

// ── SPECIALIST RUNNER ─────────────────────────────────────────────────────────
// The same agent loop from Lesson 2, parameterised by specialist config.

async function runSpecialist(specialistKey, userMessage) {
  const spec = specialists[specialistKey];
  const messages = [{ role: 'user', content: userMessage }];

  while (true) {
    const response = await client.messages.create({
      model: 'claude-haiku-4-5-20251001',
      max_tokens: 1024,
      system: spec.system,
      tools: spec.tools,
      messages,
    });

    if (response.stop_reason === 'end_turn') {
      return response.content.filter(b => b.type === 'text').map(b => b.text).join('');
    }

    messages.push({ role: 'assistant', content: response.content });
    const results = response.content
      .filter(b => b.type === 'tool_use')
      .map(t => ({
        type: 'tool_result',
        tool_use_id: t.id,
        content: executeTool(t.name, t.input),
      }));
    messages.push({ role: 'user', content: results });
  }
}

// ── SUPERVISOR ────────────────────────────────────────────────────────────────
// Uses forced tool use (Lesson 3) to produce a reliable routing decision.
// It reads the user message, picks a specialist, and hands off.

const routeTool = {
  name: 'route',
  description: 'Select the specialist best suited to handle this request.',
  input_schema: {
    type: 'object',
    properties: {
      specialist: {
        type: 'string',
        enum: ['billing', 'tech_support'],
        description: 'billing: invoices, charges, refunds. tech_support: bugs, errors, outages.',
      },
      reason: {
        type: 'string',
        description: 'One sentence explaining why this specialist was chosen.',
      },
    },
    required: ['specialist', 'reason'],
  },
};

async function supervisor(userMessage) {
  console.log(`\nUser: ${userMessage}\n`);

  // Step 1: Supervisor decides who handles this
  const routingResponse = await client.messages.create({
    model: 'claude-haiku-4-5-20251001',
    max_tokens: 256,
    system: `You are a customer support supervisor. You read incoming requests and
route them to the correct specialist. Do not answer questions yourself.`,
    tools: [routeTool],
    tool_choice: { type: 'tool', name: 'route' }, // always route, never answer directly
    messages: [{ role: 'user', content: userMessage }],
  });

  const routing = routingResponse.content.find(b => b.type === 'tool_use').input;
  console.log(`Supervisor → ${routing.specialist} (${routing.reason})`);

  // Step 2: Run the chosen specialist with the original message
  const answer = await runSpecialist(routing.specialist, userMessage);
  console.log(`\nAnswer: ${answer}\n`);
  return answer;
}

// ── TEST IT ───────────────────────────────────────────────────────────────────

await supervisor('I was charged twice for invoice INV-5512, can I get a refund?');
await supervisor('The dashboard has been returning 503 errors for the last hour.');

Key design decisions

Supervisor uses forced tool use for routing

If you ask the supervisor to "pick a specialist" in prose, it might write "I'll route this to billing" and then also try to answer the question itself. Forced tool use (Lesson 3) guarantees it only outputs a routing decision — no accidental answers.

Specialists are isolated

Each specialist has its own system prompt and tools. The billing agent cannot accidentally call check_system_status. This is the same reason you write separate NestJS modules instead of one god-service.

Parallel specialists (for independent sub-tasks)

When a request needs two specialists simultaneously — e.g. "fix my billing AND check my service status" — run them in parallel with Promise.all: 

const [billingAnswer, techAnswer] = await Promise.all([
  runSpecialist('billing', userMessage),
  runSpecialist('tech_support', userMessage),
]);
const combined = `Billing: ${billingAnswer}\n\nTech: ${techAnswer}`;

This is the Node.js equivalent of LangGraph's parallel execution (Level 4, §4.5). No framework needed — Promise.all is sufficient for I/O-bound agents.

When to add a new specialist vs a new tool

SituationSolution
Adding a 6th tool to an existing agentSplit into two agents instead
New domain with its own vocabulary and rulesNew specialist agent
Same domain, just one more actionAdd a tool to the existing specialist
Two specialists frequently collaborateConsider swarm pattern (agents hand off to each other)

▲ Senior & Staff Deep Dive Engineering tensions • staff-level questions with answers • production pitfalls
▶
⚡ Engineering tensions
Supervisor complexity vs. coordination clarity—A supervisor pattern is conceptually clean but the supervisor itself becomes a complex agent that must understand all sub-agent capabilities. If the supervisor makes routing mistakes, every downstream agent fails. Concentrated risk at the coordination layer.
Single agent simplicity vs. multi-agent parallelism—A single agent running 5 sequential tool calls takes 5× tool latency. Map-reduce running them in parallel takes 1× latency. But multi-agent adds coordination overhead, state merging complexity, and inter-agent failure propagation. The latency win must justify the complexity cost.
Sub-agent isolation vs. shared context—Isolated sub-agents prevent context overflow and enable specialization. But coordinating between them requires explicit state passing, serialization, and careful result aggregation. The coordination code often becomes more complex than the agent logic itself.
💬 Staff-level questions
Q1
Your multi-agent system has Agent A depending on Agent B's output, and Agent B depending on Agent C's output. Agent C fails. Design the failure propagation and recovery strategy.
Steer: Failures in dependency chains need to be explicit, not silent. Each agent needs to handle 'I received an error, not a result.'
Design with explicit error propagation: (1) Agent C fails — returns {status: 'error', error_type: 'tool_failure', message: '...', partial_result: None}. It never raises an exception. (2) Agent B receives the error result. It checks status before processing: if error, it returns {status: 'error', source: 'agent_c', propagated: true, message: '...'}. B should not attempt to work with missing input. (3) Agent A receives the propagated error. It decides: can it complete with partial information? If yes, proceed with a caveat. If no, propagate the error to the user with a clear explanation of which step failed. Recovery: the supervisor can retry Agent C independently (the dependency chain knows where the failure originated). Retry Agent C → if success, re-run B and A from C's corrected output. No need to re-run the entire pipeline.
Q2
When does the coordination overhead of a multi-agent system exceed the benefits? Give a concrete threshold.
Steer: Coordination overhead has a formula: serialization + routing + state merging + inter-agent latency. When does this exceed the benefit of parallelism or specialization?
Concrete threshold: multi-agent adds value when EITHER: (a) Parallelism saves more time than coordination costs: if parallel tasks each take 2s and coordination overhead is 500ms, you save 1.5s per parallel pair. Break even at: (N-1) × task_latency > coordination_overhead × N. For N=3 tasks at 2s each: single-agent = 6s, multi-agent = 2s + 0.5s overhead = 2.5s. Worth it. For N=2 tasks at 0.5s each: single-agent = 1s, multi-agent = 0.5s + 0.5s = 1s. Not worth it. (b) Context isolation is genuinely necessary: each sub-agent needs >30% of the context window just for its specialized prompt, making a single agent impossible. Rule of thumb: start multi-agent only when a single agent is actively failing due to context overflow or conflicting instructions — not preemptively.
Q3
Design an agent architecture for a task requiring both deep domain expertise and broad task management. How do you prevent the supervisor from being a bottleneck?
Steer: The supervisor's job is routing and aggregation. If it's doing domain reasoning, it's overloaded.
Strict separation of concerns: the supervisor only routes and aggregates — it has zero domain knowledge. It classifies the task, routes to the right specialist, receives structured output, and assembles the final response. The domain expert sub-agents contain all domain-specific knowledge and tools. Design the supervisor's system prompt to be domain-agnostic: 'You receive a task and a set of specialist agent results. Route tasks to the correct specialist. Combine specialist results into a coherent response.' The specialist agents' system prompts are domain-dense. Bottleneck prevention: design specialist agents to return self-contained, pre-formatted results that require minimal synthesis by the supervisor. The supervisor should spend <1 LLM call on synthesis. If the supervisor needs multiple turns to understand a specialist's output, the specialist's output schema is wrong.
Q4
How do you test a multi-agent system end-to-end when testing individual agents in isolation doesn't catch inter-agent communication bugs?
Steer: Integration tests for multi-agent systems need to exercise the communication contracts between agents.
Test strategy layers: (1) Unit: test each agent in isolation with mocked inputs that represent the structured output of other agents. Validates each agent's behavior given correct inputs. (2) Contract: define the schema for each inter-agent message. Test that Agent A's output always matches the schema Agent B expects. Use Pydantic models for these schemas and validate them in CI. (3) Integration: run the full multi-agent pipeline with a small set of real end-to-end test cases. Capture the actual inter-agent messages and verify they match the contract schemas. (4) Chaos: inject failures at specific agents and verify propagation behavior. Agent C fails — does Agent A receive the right error and produce an appropriate response? Most bugs in multi-agent systems live in the failure paths, not the happy path.
Q5
How does token cost scale in a multi-agent system compared to a single agent? At what scale does this become a real budget concern?
Steer: Each agent has its own system prompt, context, and tool schemas. These multiply by the number of agents.
Cost formula: multi-agent_cost = Σ(agent_i_system_prompt_tokens + agent_i_context_tokens + agent_i_output_tokens) across all agents. If each agent has a 2K token system prompt and receives a 1K token context, and runs for 3 turns: 3 agents × (2K + 1K) × 3 turns = 27K tokens vs. a single agent at 2K system + 1K context × 3 turns = 9K tokens. Multi-agent costs 3× more just from system prompt overhead. At scale (1M runs/month at $0.01/1K tokens): single agent = $90/month vs. 3-agent system = $270/month. Budget concern threshold: when the cost multiplier from multi-agent exceeds the productivity gain from parallelism or specialization. Always model cost before committing to multi-agent. Profile in production: log token counts per agent per run.
Q6
The swarm/network pattern has no central router. How do you debug a swarm where agents hand off incorrectly?
Steer: Without a central router, there's no single point to log all routing decisions. Debugging requires reconstructing the hand-off chain.
Debugging approach: (1) Assign a unique run_id that propagates through every hand-off. Log: {run_id, from_agent, to_agent, handoff_reason, state_snapshot} at every hand-off. (2) Reconstruct the hand-off chain from logs: SELECT * FROM agent_logs WHERE run_id=X ORDER BY timestamp. This gives you the exact sequence of hand-offs. (3) Identify the incorrect hand-off: which agent handed to the wrong agent? Look at the state_snapshot at that point — what did the agent 'see' that led to the wrong decision? (4) Fix: update that agent's routing logic (system prompt or conditional edge) to handle this case correctly. Prevention: define a finite set of valid hand-off targets for each agent type. An agent that tries to hand off to an undefined target raises an error rather than silently routing incorrectly.
🔴 Production pitfalls
Infinite agent spawningAn agent that can spawn sub-agents, where those sub-agents can also spawn sub-agents, can create exponentially growing trees. Apply a shallow hierarchy rule: sub-agents cannot spawn sub-agents. Without this, a confused agent can exhaust your API rate limits in minutes.
Token cost multiplied by agent countMulti-agent systems often cost 3–5× more than single-agent equivalents due to per-agent system prompt overhead. Model cost before committing to the architecture. Log token counts per agent per run from day one.
Missing inter-agent error contractsWhen Agent B expects a success result from Agent A but receives an error, and there's no defined error schema, B fails in an undefined way. Define explicit error schemas for every inter-agent message, not just happy-path schemas.
